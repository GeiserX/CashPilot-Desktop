# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Fixed

- **UpRock said you could cash out at $5.** Its minimum is 250 UPT. The catalog now says so, and UPT gets a price from CoinGecko, so the app can compare an UpRock balance with that minimum.
- **Redeploying a proxied copy could leave the proxy with no copy at all.** The old earner and tunnel were removed before the new tunnel started, so a tunnel that could not start (an image missing locally, a proxy that does not answer) cost the running copy. The new tunnel now starts under a staged name next to the running copy, and the old pair goes only after the new tunnel has proved an exit.
- **The Fleet page could draw over another view, and lose a half-typed proxy.** Fleet reads the backend twice before it draws, so a user who opened another view meanwhile got the Fleet page back. Any proxy action redraws the page, which also reset the open proxy editor and dropped unsaved values, a typed password included. A redraw now gives up when Fleet is no longer shown or a newer redraw started, and keeps the open editor when the same proxy's editor is drawn again.
- **The Proxies section had no help link.** It now links to the published page on proxied copies, https://geiserx.github.io/CashPilot/proxies/.
- **A proxied copy's stop that failed halfway could be undone.** The earner stopped first. If the tunnel then failed to stop, the next status read saw a ready tunnel beside a stopped earner and started the earner again. The tunnel now stops first, so a half-finished stop never leaves that state.
- **A refused delete still removed the service's proxied copies.** Deleting a service with its data, without the extra yes for unrecoverable volumes, removed every proxied copy first and only then refused. The refusal now comes before anything is removed.
- **The Proxies section offered a native-runtime service as a proxy candidate.** Picking it failed with "runs on the native runtime". The candidate list now shows that reason up front and disables the option, because only Docker can run a copy through a proxy.
- **Two apps on one Docker host could lose each other's Activity sample.** A sweep removed another app's helper the moment it exited, before its owner had read the log. Another app's helper is now removed only after it has been finished, or stuck before starting, for longer than the 30-second helper limit. A sock_diag dump the kernel ends with an error code is now an error, and a reading in which every dump of one snapshot failed is marked partial.
- **An untouched money4band `user-config.json` filled the import table with placeholder rows.** An app that is off and holds only template placeholders is now left out, as the `.env` reader already did. The import notice and guides now point proxies at the Proxies section of the Fleet page, and the guides explain the missing CashFactory Bitping row and the refusal when a saved value differs from the file. `make catalog-check` now also compares the import mapping with the web app's, so the two importers cannot drift apart unseen.

## [0.39.4] - 2026-11-06

### Fixed

- **Some provider ratings claimed more than their sources say.** The catalog now carries the web's corrected verdicts: cons and points that went past their cited source or rested on too few user reports are set to poor or unknown, and payout terms, fees and optional identity checks follow the sources. No grade letter changes.

## [0.39.3] - 2026-11-06

### Fixed

- **On Podman, every container deploy was refused, because the LAN fence cannot work there.** Podman's Docker-compatible API keeps the bridge interface name out of the network's options and drops the masquerade and inter-container options, so the fence's network check failed on every deploy of a fresh install. A Podman daemon now resolves to a mode of its own: with `auto`, earners deploy on Podman's default network and Needs attention says they are not fenced; with `on`, deploys are refused with a message that says why and how to opt out.
- **A proxied copy's tunnel container was listed as exposed, with a Turn on isolation button that could not move it.** The tunnel container's own firewall closes the LAN, so it is no longer counted as outside the fence, and it no longer makes a fresh install read as an upgraded one.
- **Two CashPilot processes on one daemon could kill each other's fence helper.** The window and the background daemon share the helper's name. Desktop now waits for a helper another process is still running instead of removing it, so neither side records a failed fence and refuses a deploy. Desktop also waits for a CashPilot worker's helper on the same daemon, but the worker (v1.70.0) still removes a running helper of that name, so a worker on the same daemon can still fail a Desktop fence write until the worker gets the same fix.
- **A Settings save or the Activity switch could turn off the app's memory that isolation was on.** Both wrote back a whole earlier copy of the config; they now write only their own fields.
- **The LAN fence helper image is pinned by digest**, `drumsergio/cashpilot-worker:1.70.0@sha256:1f0fccd1...`, like the tunnel image. It runs with host networking and `NET_ADMIN`, so a re-pushed tag must not change what it runs.

## [0.39.2] - 2026-11-06

### Fixed

- **The LAN fence left the home's public IP open, so an earner could reach a port the router forwards back into the LAN.** Most home routers loop a connection to their own public address back inside (NAT loopback). The CashPilot worker drops that address and Desktop did not. Desktop now reads this computer's public IPv4 once an hour and the fence drops it too; a failed lookup keeps the last address. Only one address is dropped, so a second WAN still needs a rule on the router. See docs/configuration.md.

## [0.39.1] - 2026-11-06

### Fixed

- **A proxy edit reaches its copies, and the cap no longer restarts a copy you stopped.** A copy started from the settings written into its tunnel when it was deployed, so a new password, port, type, Tailscale auth key or exit node was saved and ignored; every start (by hand or after a cap reset) now writes the proxy as stored into the tunnel first, and stops and restarts a tunnel still running on old settings. A host that no longer resolves stops the start instead of sending the login to the old address. At a cap crossing a copy you had stopped was marked as stopped by the cap, because stopping a stopped container succeeds, so the next reset started it; only copies that were running are marked now, and a cap lifted while a stop ran starts the copy again. The tunnel now joins the fenced network with LAN isolation on, like every other bridge earner (it joined Docker's default bridge before). Also: a copy's record is saved before it is deployed and a proxy cannot be deleted under it; a deploy whose settings cannot work fails before the running copy is removed; Test tunnels do not restart with Docker and a stale one is removed; a Tailscale login server with a user name, password, query or fragment is refused; a cap under 0.001 GB is refused; a probe answer must be an IP; Start is disabled on a capped proxy's copies; a new proxy with a reset day starts its period at once.

## [0.39.0] - 2026-11-06

### Changed

- **A is now the top grade, as on the web.** A provider whose score reaches 90% grades A, subject to the same ceilings as before, and A is drawn like B. Desktop still refuses any letter outside A to F, so the synced `services/_ratings.yml` no longer leaves every provider "Not rated yet". No provider reaches A or B today, so no grade changes.

## [0.38.3] - 2026-11-06

### Fixed

- **Isolation could switch itself off after the runtime lost the isolated network.** With every fenced earner removed, a `docker network prune` or a runtime reset left no trace of `cashpilot-isolated`, and a stopped earner on the default bridge then made the install look upgraded, so new earners went back onto the bridge, where they reach the LAN. The config now remembers that isolation was on (`isolationOn`, written when the mode first resolves to on or isolation is turned on from the dashboard, cleared by Settings `off`), and the setting, the memory or Docker's evidence each keep the app fenced. The same fix as the CashPilot worker (GeiserX/CashPilot#594).

## [0.38.2] - 2026-11-06

### Fixed

- **Proxied copies refused to start unless `CASHPILOT_TUNNEL_IMAGE` was set by hand.** The tunnel image is now pinned to `drumsergio/cashpilot-tunnel:1.69.0` by its multi-arch digest (linux/amd64 and linux/arm64); `CASHPILOT_TUNNEL_IMAGE` can point at a mirror, with an exact tag or digest only.

## [0.38.1] - 2026-11-06

### Fixed

- **The LAN fence could not run on v0.37.0 and v0.38.0, so with isolation on every bridge deploy was refused.** Its helper was pinned to `drumsergio/cashpilot-worker:1.66.0`, which has no `app/lan_fence.py`. It is now pinned to 1.70.0, the first worker image that carries the fence. The same change closes gaps review found: an earner on the fenced network and a second network is named as exposed; a network missing masquerade-off or ICC-off is refused; earners left on a removed copy of the network are started only after the table is written; `network_mode: default` is fenced like `bridge`; a leftover container is removed only if it is our helper; turning isolation on reports the status after the moves; and Needs attention shows a fence check that failed.

## [0.38.0] - 2026-11-06

### Added

- **Earn on more exit IPs by running extra copies of a service through a proxy.** Fleet gains a Proxies section. A proxy is SOCKS5 or HTTP CONNECT, with or without a login, from any provider, or a Tailscale exit node. Its definition, login and auth key are stored encrypted, and the window only learns whether a secret is set. Test reports the exit IP and country. An optional traffic cap stops every copy behind the proxy at a chosen percent, and a reset day or Reset usage starts only the copies the cap stopped. Each copy runs as two containers: a tunnel sidecar from `drumsergio/cashpilot-tunnel` (NET_ADMIN and `/dev/net/tun` only, every other capability dropped, read-only root, never privileged, no Docker socket) and the earner in the sidecar's network namespace. DNS goes through the proxy, and when the proxy dies the copy reaches nothing; it never falls back to this machine's IP. A service that needs the host network, ports, devices, extra network capabilities or whose catalog entry sets `proxy_prohibited` is refused with the reason. The cap is counted only while the app runs. This build pins no tunnel image yet, so proxied copies need `CASHPILOT_TUNNEL_IMAGE` set to an exact tag or digest.

## [0.37.0] - 2026-11-06

### Added

- **Container earners are fenced off your LAN by default on new installs.** On Docker's default bridge an earner could reach the LAN, this computer, a tailnet and cloud metadata. A new install now deploys bridge-networked earners onto CashPilot's own network, `cashpilot-isolated`, and writes one nftables table into the daemon's network namespace through a one-shot helper container: the earners' NAT plus drops for 10/8, 172.16/12, 192.168/16, 100.64/10, 169.254/16, directly connected subnets and the host. NAT and drops share the table, so a lost table means no internet rather than LAN access. The table is rewritten at startup, before every deploy and every five minutes, and a deploy that cannot be fenced is refused before the running container is touched. An upgraded install is left as it is: Needs attention names the exposed services and offers **Turn on isolation**, which redeploys the running ones with their settings and data. Settings, LAN isolation: `auto` (default), `on` or `off`. The same mechanism as the CashPilot worker (GeiserX/CashPilot#574); see docs/configuration.md. Known problem in this release and v0.38.0: the helper was pinned to `drumsergio/cashpilot-worker:1.66.0`, which has no `app/lan_fence.py`, so with isolation on every bridge deploy was refused (no earner ran unfenced). Fixed in v0.38.1.

## [0.36.0] - 2026-11-05

### Added

- **Catalog providers are graded with a letter, B at best, with their real cons and where each one comes from.** The grade is computed the same way as on the web, from the published criteria in `services/_ratings.yml` (payout record, payout terms, account safety, fit with running it in a container, traffic transparency, privacy, identity checks, support, earnings realism and longevity), and nobody types a letter: there is no A, a provider that forbids containers is held at D or below, and missing evidence counts as bad, not neutral. The catalog gains a Grade column whose tooltip is the worst con, and the service card shows the grade, any ceiling that lowered it, the top three cons and the pros, each with its source and the date it was checked. A provider with no evidence block, or one that does not pass the checks, says "Not rated yet"; a custom service is not rated. How we grade: https://geiserx.github.io/CashPilot/ratings/

## [0.35.0] - 2026-11-05

### Added

- **Bring service logins over from money4band, CashFactory or InternetIncome.** Settings, Import from another tool, takes up to four config files (64 KiB in total) or pasted text: money4band's `user-config.json` or `.env`, CashFactory's `.env`, InternetIncome's `properties.conf` with `earnapp.txt` and `proxyrack.txt`. A dry run shows each service the files set up, its fields as imported, missing, still the example value or needing a retype, secrets only as "set", and every setting left out with the reason. A value a shell or Docker Compose would expand is never guessed at, and nothing in the files is run or fetched. Saving parses the files again, stores only ready services, encrypted, and never replaces a value already set here; each saved service then deploys through the normal deploy. The mapping (`internal/importers/sources.yml`) is a copy of the web app's. See docs/migrate/.

## [0.34.0] - 2026-11-05

### Added

- **Activity: see which destinations each earner talks to, opt-in.** Off by default. While it is on, every 5 minutes a short-lived helper per earner reads the socket tables and TCP/UDP counters of the earner's network namespace and reports connection opens, failures, open connections, ports, networks (ASN), registered countries and destination kinds; it never reads packet contents. The helper is the web console's `app/procnet.py`, vendored byte for byte, and runs pinned by digest as user 65534 with every capability dropped, a read-only filesystem and no mounts. Host-network earners such as Mysterium are matched by cgroup and show destinations and alerts but no counters. Remote addresses are kept 24 hours, hourly aggregates and alerts 35 days, and switching Activity off deletes the addresses at once. Mail-port, LAN and unusual-hour alerts go to the bell and never carry an address. See docs/activity.md.
- **Packages for winget, a Homebrew tap and the AUR, ready to submit.** Each installs the exact binary the release publishes; `packaging/render.sh vX.Y.Z` writes the version and checksums into all three, and a test fails if a package names an asset the release does not publish. Nothing is submitted yet. See docs/app-stores.md.

## [0.33.1] - 2026-11-05

### Changed

- **Test fixtures and design docs no longer use real machine names, a tailnet name or a home path as sample data.** They use neutral stand-ins. Behaviour is unchanged.

## [0.33.0] - 2026-11-04

### Added

- **Run an image the catalog does not list, as a custom service.** Under Catalog, Your custom services, Add custom service takes a name, an image reference from Docker Hub or any registry (no tag or `:latest` is accepted with a warning), environment variables with a Secret tick, an optional command, an optional data path and a memory limit. The definition is stored encrypted in the app's database, never under `services/`, under an internal name `custom-<name>` that is never given out again after a delete. It deploys with the same restrictions as a catalog service with no special needs: every capability dropped, `no-new-privileges`, a process and a memory limit, never privileged, no host network, no devices, no ports, and one mount, its own named volume. Every place it shows says CashPilot has not reviewed the image; it has no collector, so its balance is a dash, and it is not exported to compose. A secret's value is never sent back to the window. The catalog loader now skips any entry with the reserved `custom-` prefix, and a deploy refuses to replace a container labelled as another service or another copy. See docs/custom-services.md.

## 0.11.0 to 0.32.0

These releases are not split by version here. Each release's own notes are on GitHub: https://github.com/GeiserX/CashPilot-Desktop/releases

### Added

- **The dashboard graphs what each container costs this machine over time.** Under "Earned per day" there are three small line charts: CPU (100% is one core), memory, and network down and up as a rate, on the same 7-day (hourly points) or 30-day (6-hour points) window, with a container picker whose default is all containers. Desktop reads every running unit every five minutes and keeps one row per container per hour for 35 days. An hour with no reading is a gap in the line, never 0. A host-network container has no traffic counters of its own, so its traffic stays unknown and a network total without it is shown with ≥.

### Fixed

- **The Mysterium balance was a trailing 30-day sum, so it rose and fell as days left the window.** MystNodes' cloud `earningsTotal` is not a balance, and its per-node lifetime comes back as 0. Where the catalog declares `collector.node_read`, Desktop now reads each Mysterium node's own unsettled balance and lifetime from its TequilAPI and stores the unsettled total as the balance, each node once. A node in Docker is read by running the catalog's read-only command inside its container. A node Desktop runs natively is read over its local TequilAPI on 127.0.0.1:4050, and that text goes through the same regexes. The per-node view shows each node's own lifetime. When no node on this computer can be read, the dashboard says no node was read and offers Retry, not new credentials, and no 30-day figure is stored. A node on another machine is not read.
- **A provider that disabled the account looked like a container to restart.** IPRoyal Pawns prints "user is disabled" and exits on every start, so the dashboard showed a Down row with Start, an Unstable row and a No reading row with Fix credentials, and none of them can help. Desktop now reads the log of the container's last run only, since its last start, when the catalog entry declares an `account_disabled` signal, so an earlier run's refusal is never judged as the current one. It then shows one "Account disabled" card for the service with a link to the provider's support page. Start is not offered for it, in the card or the services table. The catalog also gains `support_url` and Mysterium's `collector.node_read`, which the loader now reads; a health signal with a state the web catalog rejects is dropped at load instead of being read as a failure.
- **A busy Anyone Protocol relay could outgrow its 1536 MB memory limit and be killed.** anon sizes its cell queues from the host's RAM, not the container's limit. The catalog now deploys `drumsergio/cashpilot-anyone:0.4.10.2-r2`, which sets `MaxMemInQueues` to half the limit (768 MB) unless the relay's `anonrc` sets one.
- **On Windows, a VPN customer of the native Mysterium node could reach the user's tailnet and LAN.** The node reads `--firewall.protected.networks` on Linux and macOS but not in its default Windows mode, which also needs admin rights and a TAP driver Desktop does not have. The Windows binary now runs with `--userspace`, whose netstack refuses customer connections to 10/8, 172.16/12, 192.168/16 and 127/8 without admin rights. That netstack reads the node's built-in list, not the flag, so Desktop adds an outbound Windows Firewall rule that blocks `myst.exe` from 100.64.0.0/10 (CGNAT and Tailscale) and 169.254.0.0/16 (cloud metadata). Creating the rule takes one Windows admin prompt on deploy. The node does not start without the rule, and removing the service deletes it. A Windows node deployed before this release keeps its old launch until it is deployed again.
- **EarnApp ran a 2022 client that nobody maintains any more.** The catalog deployed `fazalfarhan01/earnapp:lite`, a community image frozen at EarnApp 1.294.218. It now deploys CashPilot's own image, `drumsergio/cashpilot-earnapp:1.665.73-r1`, which holds no Bright Data code: at first start it downloads the pinned EarnApp build from Bright Data's CDN, checks its sha256 and runs it in lite mode. It ships amd64, arm64 and arm/v7 and needs no added capabilities. The "Accept Terms" (`EARNAPP_TERM`) field is gone because the new image does not read it; the node UUID is still the only setting. The node UUID must now be `sdk-node-` followed by 32 lowercase hex characters, as `earnapp showid` prints it: the new image refuses any other form at start, so the deploy refuses it first instead of letting the node exit on every restart.
- **A new Anyone Protocol relay crash-looped as soon as it was deployed.** The vendor image starts as root and needs CHOWN, DAC_OVERRIDE, FOWNER, SETUID and SETGID to fix its own folders and drop to its relay user, and Desktop drops every capability the entry does not declare. The catalog now deploys CashPilot's own image, `drumsergio/cashpilot-anyone:0.4.10.2-r1`, built from the project's signed `anon` package and running as `anond` from the start, so it needs no added capabilities on amd64 or arm64. The fingerprint hint now says `docker exec cashpilot-anyone-protocol cat /var/lib/anon/fingerprint`.
- **The Linux build trusted certificates anyone could mint, through eight compromised eMudhra intermediates.** Their private keys were recoverable and they were revoked on 18 October 2026, but on Linux Go checks certificates itself and never asks about revocation, so the Go 1.26.9 that built every release accepted a forged certificate for any provider the collectors sign in to, password and all. Releases are now built with Go 1.26.10, which distrusts the eight in its own certificate check. The macOS and Windows builds hand the check to the operating system, which already refuses them.
- **An exported compose file with an unfilled host path failed with an error that named nothing.** Storj's identity and data directories come from the `.env` file beside the export; when one was missing, Compose substituted an empty string and refused the file with "empty section between colons". An unfilled path is now written as a required variable, so Compose refuses with "required variable IDENTITY_DIR is missing a value" and says what to set.
- **Mysterium's WebUI address accepted octets over 255 and non-ASCII digits.** `256.0.0.1` or an address in Arabic-Indic digits passed the check, and the node's listener would fail to bind while the node kept running. Each octet is now 0 to 255 in ASCII digits.
- **A Storj node could be killed ten seconds into a stop, whatever the catalog allowed.** The image runs supervisord, which kills the node 10 seconds after any stop because its program section sets no grace period, and a node killed mid-flush restarts with an unclean-shutdown recovery. The catalog now wraps Storj's entrypoint to give the node 270 seconds inside supervisord, within the container's 300. An exported compose file carries the wrapper with every `$` escaped, and a service that declares no stop grace now exports the 30 seconds the app itself gives it, instead of leaving it on Docker's 10.
- **Mysterium's WebUI can sit behind a reverse proxy again.** A new WebUI address field defaults to 127.0.0.1 and takes a comma-separated list, so a machine can add the one address its proxy connects to. The value lands on the node's command line, so it must match the catalog's pattern before it is saved or deployed; "127.0.0.1, 10.0.0.1" with a space is refused instead of stopping the node.
- **Storj said it paid in STORJ token, at a $4 minimum, over zkSync. None of that is true any more.** Storj pays node operators in USDC on Ethereum mainnet from the October 2026 payout, ended zkSync Era payouts on 1 September 2026, and pays a wallet only when the transaction fee is at most a quarter of the amount, so the minimum moves with gas and smaller balances roll into the next month. The entry says so, the wallet field asks for a self-custodial Ethereum address, and the node no longer starts with the sunset zkSync wallet feature. The payout card shows no minimum rather than a wrong one.
- **Mysterium's WebUI and API were published on every interface of the machine.** The catalog started the node with both bound to 0.0.0.0 under host networking, which Desktop had bound to loopback last July and lost when it began vendoring the web catalog verbatim. Both bind to 127.0.0.1 again; nothing off the machine needs them, and the guide shows the SSH tunnel for the WebUI.
- **Earnings went missing whenever two copies of the app were running.** The window and the background daemon share one database file, and only one of them may write at a time. The other used to be told "database is locked" and simply gave up, so a collected balance was thrown away with nothing on screen to say so — the dashboard kept showing the older number as if it were current. A write now waits for its turn instead of failing, and a test runs both copies at once and fails if a single row is lost.
- **Removing a service deleted data that cannot be got back.** Remove deleted every named volume the container had, behind one confirmation that said "this deletes the managed container and its Docker volumes". For Mysterium that volume is the node's identity keystore; for Storj it is an identity whose ID is proof-of-work bound, takes hours to regenerate, and whose loss forfeits the held payout balance. There is no backup of either. Removing a service now removes the container and leaves the data alone. Deleting the data is a separate question that names each volume and quotes what each one holds, and answering yes to that question is the explicit permission the runtime demands before it will touch a volume the catalog marks unrecoverable — without it the removal is refused by name, before anything is removed. Keeping the data says so afterwards, and says how to delete it later.

- **Containers ran with more of the kernel than they needed.** These images are third-party and closed-source, and they ran as in-container root with Docker's full default capability set, which includes `NET_RAW` — raw sockets on the bridge network, so ARP and DNS spoofing against everything else on it — plus `MKNOD`, `SETUID` and `SYS_CHROOT`. Every container now starts with all capabilities dropped and only the ones its own catalog entry declares added back, with `no-new-privileges`, a PID ceiling (override with `CASHPILOT_PIDS_LIMIT`), host devices only from the runtime's own allow-list, and privileged only where the entry asks for it — the same policy the CashPilot worker applies. On a Docker Desktop switched to Windows containers, whose daemon rejects capability options outright, the Linux-only parts are left off rather than failing every deploy.

- **Services were killed after 20 seconds no matter what they asked for.** Storj declares a 300-second stop timeout because a storage node has to flush before it goes, and being SIGKILLed early costs an unclean-shutdown recovery on the next start. Stop, restart, redeploy and remove now all read the grace period out of the service's catalog entry, every time — so a node that has been running since before this change gets its 300 seconds without being redeployed first — and a redeploy stops the old container cleanly before replacing it instead of killing it outright.

- **A redeploy could move a node's data and bring it back as a different node.** The replacement container mounted what the catalog says rather than what the running container actually has, so a service whose data lives somewhere the catalog does not know about — set up by hand, or moved outside the app — came back on the catalog's own volume, with a new identity and no reputation. A redeploy now keeps every mount where it already is, unless the user typed a new path for it on this deploy, and says so while it deploys. The path it reuses is the one that was asked for, not the one the daemon reports: Docker Desktop and Podman Desktop run the daemon inside a Linux VM and answer with the folder's path inside that VM, which is a path the user never typed and one the daemon can refuse to mount.

- **The deploy history named an image the deploy never pulled.** An entry that ships a different image per architecture — traffmonetizer publishes its ARM builds as separate tags — was logged under the entry's default, so the one line somebody reads when an image turns out to be the problem was wrong on every ARM machine. It now records what was actually pulled.

- **Raspberry Pi and other ARM machines pulled the wrong image.** Traffmonetizer publishes separate arm64 and 32-bit ARM builds as separate tags and labels every one of them `linux/amd64`, so Docker cannot pick the right one; the per-architecture override in the catalog was parsed and never used. The deploy now asks the DAEMON which CPU it runs on — on Docker Desktop that is the Linux VM's, not the desktop app's — and pulls, creates and records the image for it. An entry that publishes no build for this machine says so while deploying, and still deploys.

- **The service catalog was months out of date, and some of it was earning nothing.** Desktop shipped its own hand-edited copy of the catalog with no way back to the CashPilot web repository it came from, so corrections made there never arrived. What that cost, concretely:

  **Mysterium was deployed without SETUID, SETGID or `/dev/net/tun`.** The node configures its interface and firewall through `sudo`, which switches uid and gid on the way (`setresuid`, `setgroups`), so it needs both capabilities wherever they are not granted by default; the entry now asks for them. It also needs a TUN device for wireguard, and Desktop was never mapping one: the catalog declared `docker.devices`, the loader parsed it and the runtime built its container without it. The device is now mapped, against a fixed allow-list that a catalog entry cannot widen on its own — anything outside it fails the deploy instead of producing a container that cannot work. Both failures used to earn nothing while showing green: the node registers, appears in discovery, and carries no traffic.

  **Bitping was deployed with no credentials.** Its `BITPING_EMAIL` and `BITPING_PASSWORD` were dropped from an earlier catalog rewrite while the image kept reading them, so the container sat at "No active session" indefinitely. It also now requests `NET_RAW`, which its network probes need wherever the default capability set does not include it.

  **Presearch was offered as an active service.** The programme is gone; the entry is `dead` and it no longer appears, along with its signup link.

  **Repocket's container used the wrong environment contract** (`REPOCKET_EMAIL`/`REPOCKET_PASSWORD` rather than `RP_EMAIL`/`RP_API_KEY`, which is an API key from the dashboard, not the account password).

  **Ten entries listed the wrong architectures.** Nine were narrower than the registry actually publishes (EarnApp, Earn.fm, Honeygain, IPRoyal Pawns, Mysterium, PacketStream, Storj, Traffmonetizer and SpeedShare all gained 32-bit ARM or armv5); ProxyLite was wider, claiming an arm64 build that is not published. Traffmonetizer also gains the per-architecture image overrides for its two real ARM builds — Docker Hub labels every tag of that image `linux/amd64`, so Docker cannot pick them itself.

  **ProxyBase Markets is new**, and Storj now declares a 300-second stop timeout — a node SIGKILLed after the default 30 seconds loses in-flight pieces and audit score.

- **Repocket could not collect earnings at all.** The web catalog renamed the container's environment to `RP_EMAIL`/`RP_API_KEY`, which is the right contract for the container — but the earnings collector signs in to Firebase with the ACCOUNT password, and the form stopped asking for it, so every collection answered "Repocket email and password are required". The collector-only credential fields now live in the backend next to the collectors that read them, and a test fills each collector from the form's own keys and fails if it cannot get as far as its request.

- **A retired service could still be deployed.** `dead`, `dropped` and `broken` hide a service's card, and nothing on the deploy path looked at status, so a stale wizard selection or a direct call would still pull the image and start a container for a programme that is gone. Deploy and credential validation now refuse, before the pull.

- **The weekly drift check could not tell a network failure from real drift.** Every failure exited 1 and the workflow printed "services/ no longer matches the CashPilot web catalog", so a codeload outage on a Monday looked like a catalog that had changed, naming files nobody had touched. `-check` now exits 1 only for real drift and 2 when the comparison could not be made, a transient fetch failure is retried twice before it counts, and `-ref` takes a tag or a commit SHA rather than 404ing on anything that is not a branch.

- **Bytebenefit's referral link was missing from the README.** The service is live in the catalog with a referral code; the README listed neither, so anyone reading it signed up through a bare link that pays nothing. It is in the Desktop-only table now, and a test fails when any live entry's signup link is absent from the README or has had its code stripped. The README also said 50 services when 11 of those are retired entries the app hides.

- **`make catalog-check` reported the whole catalog as drifted on Windows.** Git for Windows checks files out with CRLF by default, and the comparison was byte for byte. A `.gitattributes` keeps these paths LF on every platform, and the comparison no longer counts a line ending as a change.

### Added

- **The dashboard says which services keep state that exists only on this disk, and lets you back it up.** Mysterium, ProxyBase, Anyone, Storj and Sia hostd keep a node identity, a keystore or a wallet in a volume the catalog marks critical. A **Back these up** card lists each one with the volume and what it holds, and two buttons: **I have a backup**, and **Download backup**, which reads only those volumes with the container paused, encrypts them with ChaCha20-Poly1305 to a passphrase (12+ characters) or an X25519 public key, and saves a `.cpbackup` file. CashPilot keeps nothing that could open it, refuses anything over 256 MB, and has no upload or schedule. A confirmation lapses when the volume is recreated or moved, or after six months; when every service is confirmed the card folds to one line. `cpbackup decrypt` writes one tar per volume for a restore (docs/backup.md). The file format is the web app's, so either app's tool opens either app's backups.

- **Run a service more than once on this machine.** The service's card in the setup wizard has an **Instances** box. Each extra copy is its own container (`cashpilot-<service>-2`, `-3`, ...) and registers as its own device, because every device name the catalog derives from this computer's name gets `-2`, `-3` added. That helps only where a provider pays per device and allows several per IP: the copies share one connection, so they add devices, not bandwidth. The box is locked at 1, with the reason under it, where a provider allows one device per IP, where the service keeps data in a host directory or publishes a host port, and where it runs here as a program rather than a container. The count is saved with the deployment and every redeploy keeps it; lowering it removes the highest copies first, and removing the service removes them all. Each copy gets its own dashboard row with Logs and Stop or Start. The web app has the same box.

- **Run a service from an image you choose.** The service's card in the setup wizard has an **Advanced** section with an **Image** box. Blank means the catalog image; anything else is run instead, for example a registry mirror or a community build for an architecture the provider does not publish. The choice is saved with the deployment and every redeploy keeps it until you clear the box. Only the image changes: capabilities, devices, ports, the entrypoint and the stop timeout still come from the catalog entry, and a per-architecture override never replaces a chosen image. The image does receive the service's credentials, so use one you trust. Such a deployment carries a **custom image** badge, and "update available" is judged against the chosen image, not the catalog's. The web app has the same box.

- **Export a compose file and keep earning without CashPilot.** A service's card now saves a `docker-compose.yml` you can run with Docker, Podman, Portainer or a box's own GitOps. It is written for the machine you pick — this one by default, or x86-64, 64-bit ARM or 32-bit ARM for a box you are writing it for — which matters for Traffmonetizer, whose ARM builds Docker cannot choose from the manifest. It carries no credentials: every value you own is a `${VAR}` placeholder Compose fills from a `.env` file beside it, so the file is safe to keep in a repository or send to another machine. The values it does carry — a device name, a disk allocation — are written so the same `.env` file can change them, and the header lists each one with what it is set to. Device names are this computer's name, and the header says so: running the file on a second machine without changing them puts both machines under one device, and some providers then pay for only one of them.

  It is no weaker than a CashPilot deploy — it carries the hardening the CashPilot server's worker runs these images under, which is every capability dropped and only the declared ones added back, no new privileges, a PID ceiling, the declared memory ceilings, the declared devices and stop grace period. It keeps the `cashpilot.*` labels too, so CashPilot still finds and watches those containers even though it did not start them.

  Choosing a CPU the image has no build for is refused, with the builds it does publish named, rather than written into a file that dies with "exec format error" on the machine it was made for. The wizard's preflight answers that question, so the export and the deploy step agree.

  One gap it does not paper over: Traffmonetizer's two ARM builds are exported as moving tags. Every other image in the catalog is pinned to an exact build, and those two cannot be until the catalog overlay can pin a per-architecture image.

- **The card now says what the catalog already knew.** Where a provider hides its token, the minimum before you can cash out and the unit it is counted in, how and how often you get paid, and what the service does with your connection and your account. A value nobody has documented shows as an em dash rather than a zero, because "no minimum documented" and "the minimum is zero" are different facts and one of them says you can cash out today. A balance is never counted down against a minimum in another unit either: Storj reports dollars while its minimum is in STORJ, and the two are not the same number.
- **A service can now be running and still be reported as earning nothing.** "Running" is the container's own word for itself, computed from starts and crashes, so a service that has produced nothing for a month showed a green pill and no hint that anything was wrong — the most common complaint in this whole category, and the one thing container state cannot see. Deployed services now carry a second, separate verdict next to the status pill: **not earning**, with the reason on hover, when the service's logs match a failure its catalog entry declares (Mysterium's node that registers, appears in discovery and fails every session at setup, for one) or when the container runtime reports it as restarting, because a container that keeps restarting never runs long enough to earn. Anything that could not be established reads **earning not checked** rather than passing for healthy — most services have no known failure to look for yet, and quiet logs are the absence of evidence, not a clean bill of health. There is deliberately no green "earning" badge: nothing visible from a container proves that money moved.
- **Before you deploy, CashPilot now tells you what will stop that service earning on this machine.** The catalog shows one earnings range per service and nothing else, so nobody was told that EarnApp's provider forbids containers and closes accounts that use them, that ProxyLite publishes no ARM build and its container will never start on a Raspberry Pi, or that another machine in the fleet already runs the service the provider allows one of per connection. You found that out weeks later, from a service that had earned nothing.

  The deploy step of the wizard now shows a verdict — looks fine, check these, will earn less, will earn nothing here — with the sentences behind it, and a list of what was NOT checked, so a clean result is not mistaken for a promise about things nobody looked at. It never blocks: the Deploy button stays live under the worst verdict, because that risk is yours to weigh, not ours to forbid. The CPU check asks the container runtime which architecture it runs on rather than assuming the app's own, since a virtual machine or a remote runtime is a different machine; when the runtime cannot be reached the answer is "not checked", never a guess. The one thing Desktop cannot see is whether your other machines use the same internet connection as this one, so a per-connection conflict is stated as something to check rather than as a fact, and the summary above it says you may earn nothing rather than that it should work. Where a provider ships its ARM build as a separate image, as Traffmonetizer does, the verdict describes the image Desktop actually deploys, which is the x86-64 one: a build the user will never be given is not a pass.

- **`services/` is now vendored from the web catalog, with a weekly drift check.** `make catalog-sync` fetches `GeiserX/CashPilot@main`, copies each entry byte for byte, and deletes anything upstream retired. The differences Desktop keeps are declared in `catalog-overlay/` and nowhere else: the immutable image digest pins, and the `native:` block that lets Desktop run a service as a supervised process with no container runtime. The sync refuses to run when a pin names a different repository or tag from the web entry, which is what stops a provider's image move leaving Desktop on a retired build that looks healthy and earns nothing.

  A scheduled weekly workflow runs the same check and fails loudly when the two have parted. It deliberately does not run on pull requests: a change in the web repository is not a reason to block an unrelated Desktop PR.

- **The catalog loader now reads the whole web schema.** Capabilities, host devices, per-architecture images, critical volumes, health signals, the advertised-address variable, stop timeouts, referral codes, payout and disclosure blocks, credential hints, and the preflight fields (`container_prohibited`, per-IP limits) all parse. Host devices and capabilities now reach the container; the rest arrive and wait for the slice that uses them, which is what lets that slice happen without another round of catalog surgery. A test strict-decodes every vendored entry, so a key the web catalog adds or renames fails on the sync PR rather than being dropped in silence.

  Two of them are deliberately nullable, because absent and zero are different answers: a per-IP device limit of `null` means nobody has documented one and a second instance needs checking against the provider's terms, while `0` means the provider states it imposes none. `referral.program` is the same shape — `null` is "unchecked", not a verified "no".

- **A paired Desktop shows the account-wide picture, and an unlinked one goes back to its own.** While paired, the dashboard gains an "Across your CashPilot account" panel with what the platforms this machine runs earned on your provider accounts over the server's reporting window, straight from the heartbeat response. Unlink and it disappears, leaving exactly the local numbers as before — which works because pairing COPIES this machine's history upstream rather than moving it.

  Two things it is careful about. A platform the server has no reading for renders as **—**, never `0.00`: no reading usually means a collector that does not exist yet or credentials nobody entered, and showing zero would report a loss that did not happen. And a platform running on more than one machine is marked **shared**, because earnings are collected per platform from the provider — if two machines run the same service the provider reports one balance and nothing can split it, so the figure is the account's rather than this machine's.

- **Pairing hands the server the history collected before it.** A Desktop that ran standalone for months and was then paired used to appear on the fleet page starting from the day of pairing — every earlier day it had recorded was simply absent from the total, with no way to get it there. The first time a CashPilot server confirms this worker, Desktop now uploads its recorded daily balances to `POST /api/workers/earnings-import` (requires CashPilot v1.16.0 or newer).

  It is a **copy, not a migration**: the local rows are read and left exactly where they are, so unlinking leaves this machine still showing precisely what it earned on its own. The server files the readings under this client's own source rather than merging them into its own series, because earnings are clamped deltas between consecutive balance readings — interleaving two samplers of one provider account makes every apparent drop clamp to zero and understates the total. Separate series are differenced separately and then summed.

  Sent once per server, recorded in `upstreamHistoryPushedTo`; pairing with a different server hands it the history too. A failed or partial upload is retried on the next heartbeat rather than recorded as done, and the import is idempotent so a retry costs nothing. The upload waits until this worker is fully enrolled — a client still presenting the shared enrollment key is refused by the server, since every worker holds that key and it cannot prove who is writing. Historical readings carry no exchange rate: Desktop does not record what a currency was worth on a past day, and stamping today's rate onto a year-old reading would misprice it confidently.

### Changed

- **The app now looks and reads like the web console.** One top bar replaces the sidebar, the synthwave theme gives way to graphite with hairlines, and colour marks state only. The dashboard opens on the balance, then a **Needs attention** list of stopped containers, unreadable balances and outdated images, each with the button that fixes it, then earnings per day (7 or 30 days, as bars) and the services table, which gains Health and Payout columns and keeps a row for every platform CashPilot reads, deployed here or not. The catalog is one table with the services running here first. Fonts (IBM Plex Sans at a 16 px body, IBM Plex Mono for figures) are bundled, so the app still renders offline.
- **`dropped` services are hidden alongside `dead` and `broken`.** A service that was evaluated and then removed is not on offer, for the same reason a dead one is not: listing it invites a signup that will never pay.

## [0.10.0] - 2026-07-11

### Changed

- **Fleet server — per-worker keys.** The fleet heartbeat API (`/api/workers/heartbeat`) now issues each device its own key on first contact — returned once as `worker_key` — and requires it thereafter. The shared fleet token (`CASHPILOT_API_KEY`) becomes an enrollment-only bootstrap credential and is rejected for a device once it has confirmed its own key, so a leaked device key is scoped to that device and no device can impersonate another. A fresh key is re-delivered on each heartbeat until the device confirms it, so a dropped response can't lock a device out. Interoperates with the CashPilot web UI (v1.0.0) and the CashPilot-android client. A forward-only SQLite migration adds the per-device key columns.

  Enrollment is trust-on-first-use: the shared token still lets its holder enroll a device identity, so keep the shared token secret and keep the fleet API on loopback (the default `FleetBindAddress`) unless you deliberately expose it to a trusted LAN. The heartbeat endpoint is per-IP rate-limited, and the key state machine is serialized so concurrent/retried heartbeats and the stale-device reaper cannot race a device's key. The API speaks plain HTTP — do not bind it beyond loopback/a trusted LAN without a TLS-terminating reverse proxy in front (full built-in TLS is a planned follow-up).
